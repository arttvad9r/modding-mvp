## A01 — P1: некорректный request-target завершает web-процесс

**Место:** [apps/web/src/ui.ts:740](../../apps/web/src/ui.ts#L740), [apps/web/src/main.ts:85](../../apps/web/src/main.ts#L85).

`createPrivateBetaWebHandler` выполняет `new URL(request.url, ...)` вне обработки ошибок. Сервер вызывает async-handler через `void handler(...)` без `.catch`. Некорректный URL поэтому превращается в необработанный rejected Promise.

**Воспроизведение:** изолированному HTTP-серверу с тем же handler/callback отправлен `GET //[ HTTP/1.1` через TCP, без токена. Node 26.11.1 завершился с кодом 1 и `ERR_INVALID_URL`, HTTP-ответ не отправлен. PostgreSQL и LLM для этого не нужны.

**Последствие:** один неаутентифицированный запрос может уронить непосредственно доступный Node web process. Достижимость через конкретный production reverse proxy этим аудитом не проверена; proxy может отклонять такой target раньше.

**Исправление:** обрабатывать разбор URL на внешней HTTP-границе и гарантированно перехватывать rejection handler. Некорректный target должен давать bounded `400`, а следующий `/health/live` — успешно отвечать. Не полагаться на restart контейнера как на обработку ошибки.

## A02 — P1: Repair может менять незаявленную семантику и отличать проверку от установки

**Место:** [packages/agent-core/src/repair.ts:24](../../packages/agent-core/src/repair.ts#L24), [repair.ts:364](../../packages/agent-core/src/repair.ts#L364), [packages/agent-core/src/pipeline.ts:322](../../packages/agent-core/src/pipeline.ts#L322), [packages/factorio-harness/src/harness.ts:38](../../packages/factorio-harness/src/harness.ts#L38). Контракт: ADR-0010, technical spec, product principle «false success is worse than failure».

Манифест ограничивает имена файлов и размер текста, но `dataLua` остаётся произвольным Lua. Исходные assertions проверяют запрошенные адреса; они не доказывают отсутствие дополнительных изменений. Присутствие companion-validator доступно кандидату через Factorio `mods`.

**Первое воспроизведение:** fake Repair возвращает правильный `data.lua` для steel furnace ×2 и добавляет `data.raw["furnace"]["stone-furnace"].crafting_speed = 100`. Реальный Factorio и исходные assertions проходят; Repair возвращает `repaired`, хотя ModSpec не запрашивал изменение stone furnace.

**Второе воспроизведение:** к правильному кандидату добавлено:

```lua
if not mods["zz-project-semantic-validator"] then
  data.raw["furnace"]["steel-furnace"].crafting_speed = 99
end
```

С companion-validator Repair успешно проходит исходное ожидание скорости **4**. Тот же manifest затем загружен реальным Factorio без companion-validator; диагностический `log` показал скорость **99**, загрузка прошла. Assertions не заменялись, дополнительные файлы не добавлялись.

**Последствие:** file/schema bounds и исходные assertions не обеспечивают заявленную невозможность расширить intent. Проверенный кандидат может вести себя иначе в установленном ZIP. Это проблема целостности результата; выполнение host shell в этом сценарии не продемонстрировано. Обычный детерминированный путь не зависит от такого Lua; дефект проявляется на Repair-ветке.

**Исправление:** сохранить принятый запрет изменения ModSpec, но ограничить сам язык исправлений: reviewed AST/typed repair operations либо application-owned шаблоны с проверкой изменённых prototype-адресов. Если сохраняется произвольный Lua, нужна отдельная проверка реального итогового состояния без наблюдаемого кандидатом validator и проверка отсутствия незаявленных изменений. Простая блокировка строки `zz-project-semantic-validator` не устраняет общий класс проблемы. До архитектурного решения можно возвращать явный failed вместо выполнения произвольного Repair-кандидата.

Изменение модели доверия/контракта Repair требует ADR; сохранение прежних гарантий посредством более строгой реализации следует явно документировать. Добавить оба negative integration-сценария.

## A03 — P1: у LLM-вызовов нет дедлайна; heartbeat может удерживать зависшую генерацию

**Место:** [packages/llm/src/openai-chat-completions.ts:125](../../packages/llm/src/openai-chat-completions.ts#L125), [packages/llm/src/openai-responses.ts:114](../../packages/llm/src/openai-responses.ts#L114), [packages/service-core/src/worker.ts:272](../../packages/service-core/src/worker.ts#L272).

Оба HTTP adapter вызывают `fetch` и `response.json()` без application-owned timeout/AbortSignal. Глобального дедлайна `executor.execute` тоже нет. Пока execute не завершён, heartbeat продолжает обновлять `running`; stale recovery не считает такую запись потерянной. Failover ждёт ошибку primary, а не ограничивает его ожидание.

**Воспроизведение:** injected `fetchImpl` не завершает запрос; вызов остаётся pending, в options отсутствует `signal`. Статический анализ подтверждает отсутствие дедлайна и для чтения тела. Также тело ответа читается целиком до schema validation без ограничения байтов.

**Последствие:** медленный/зависший provider может занять единственный beta worker; очередь накапливается, запросы не получают terminal state. Внутренние сетевые таймауты Node не заменяют контракт полного срока вызова, особенно при медленно продолжающемся response body.

**Исправление:** задать timeout на весь provider call, включая чтение bounded body; нормализовать истечение в retryable `process_error`, запускать fallback по существующей typed policy. Согласовать общий бюджет генерации, pg-boss expiration и recovery; отмена должна завершать реальную операцию, а не только `Promise.race`. Проверить hanging headers, hanging body, slow stream и failover.

## A04 — P1: сбой до claim оставляет вечное `queued` без рабочего задания

**Место:** [apps/worker/src/runtime.ts:72](../../apps/worker/src/runtime.ts#L72), [packages/service-core/src/worker.ts:268](../../packages/service-core/src/worker.ts#L268), [worker.ts:451](../../packages/service-core/src/worker.ts#L451), [packages/service-postgres/src/queue.ts:7](../../packages/service-postgres/src/queue.ts#L7). ADR-0014 запрещает автоматический retry jobs.

Если pg-boss уже передал job worker, а первое чтение generation/claim завершается ошибкой, job становится failed при `retryLimit: 0`. Generation остаётся `queued`. Recovery рассматривает только stale `running`; owner retry доступен только для terminal `failed`.

**Воспроизведение:** в отдельном PostgreSQL 18.6 выполнены проектные миграции, atomic submission и настоящий pg-boss consumer. `repository.get` до claim принудительно бросил transient DB error. Получены `jobState=failed`, `generationState=queued`; recovery даже с временем +1 час вернул `scanned=0`, `recovered=0`.

**Последствие:** пользователь не дождётся результата и не сможет повторить это задание через retry endpoint. Атомарность submission не закрывает отказ на consumption boundary. Падение процесса между fetch job и claim даёт тот же класс рассогласования.

**Исправление:** reconciliation для persisted queued records и потерянных/failed jobs, либо надёжная компенсация preclaim failure. Завершать такие records retryable failed, сохраняя явный owner-triggered retry и запрет автоматического повторного исполнения. Не переводить нормальные queued records в failed только из-за длительного ожидания backlog. Проверить DB outage и crash window после fetch.

## A05 — P1: retry неудачной ревизии теряет базовый ModSpec

**Место:** [apps/web/src/api.ts:382](../../apps/web/src/api.ts#L382), [api.ts:390](../../apps/web/src/api.ts#L390). Связанные решения: ADR-0014 и ADR-0016.

Endpoint копирует owner и `current.prompt`, но не переносит `baseModSpec` и `sourceGenerationId`. Для follow-up prompt вида «сохрани остальное, увеличь скорость ещё на 25%» этого недостаточно. Worker выберет обычный Planner вместо Revision Planner.

**Воспроизведение:** owner-scoped failed record имел исходный `baseModSpec` и lineage. `POST /retry` вернул `202`, но новый persisted record не имел обоих полей. Проверены данные, переданные submission store, а не только публичный ответ, из которого baseModSpec намеренно скрывается.

**Последствие:** явный retry того же пользовательского действия становится другим действием; существующие изменения могут потеряться, а относительные значения — получить другую базу.

**Исправление:** переносить snapshot и source lineage для retries ревизий. Source generation не изменять. Добавить API→worker regression на transient failure follow-up. Уточнить взаимодействие ADR-0014/0016; отдельное retry-parent поле для этого исправления не обязательно.

## A06 — P2: Factorio `write-data` и lock не изолированы

**Место:** [packages/factorio-harness/src/harness.ts:205](../../packages/factorio-harness/src/harness.ts#L205).

Harness изолирует моды и output save, но не задаёт отдельный config/write-data. Локальный Factorio config содержит `write-data=__PATH__executable__/../..`; разные проверки используют общий `.tools/factorio/.lock` и общие runtime logs.

**Воспроизведение:** четыре отдельных Node-процесса одновременно вызвали harness для корректного минимального мода. Один прошёл, три получили `Couldn't acquire exclusive lock ... Resource temporarily unavailable`. Harness классифицировал их как `factorio_load_failed`, то есть Repair-eligible ошибку мода. Service E2E, запущенный с перекрытием другого Factorio suite, упал; отдельно он прошёл.

**Последствие:** параллельные проверки/worker processes конфликтуют, инфраструктурный сбой расходует Repair attempts и может давать nonretryable failure. В одном Node-процессе `spawnSync` дополнительно блокирует event loop, heartbeats и реальную параллельность. Текущий Compose concurrency=1 снижает риск обычного одиночного production-пути, но не обеспечивает изоляцию между процессами.

**Исправление:** выделять config и writable runtime state внутри workRoot, использовать async subprocess с timeout и bounded output. Добавить multi-process integration test и проверить своевременность heartbeat при Factorio execution. Не устранять дефект простым отключением параллельных тестов.

## A07 — P2: heartbeat прекращается до публикации ZIP

**Место:** [packages/service-core/src/worker.ts:290](../../packages/service-core/src/worker.ts#L290), [worker.ts:331](../../packages/service-core/src/worker.ts#L331), [worker.ts:364](../../packages/service-core/src/worker.ts#L364).

После execute worker останавливает heartbeat и фиксирует `finishedAt`, затем ждёт artifact upload. При upload дольше stale threshold recovery может перевести всё ещё активное задание в failed. Upload способен завершиться после этого; terminal CAS вернёт ранее созданный failed record, а private object останется без успешной generation. API ArtifactStore не предоставляет cleanup port.

**Воспроизведение:** controlled artifact store выполняет recovery после продвижения часов на 2 секунды при допустимом stale threshold 1 секунда. Объект успешно возвращён store, но recovery имеет `recovered=1`, итоговый generation status — `failed`. Это воспроизведение границы lifecycle с fake store, не утверждение о фактической задержке beta SeaweedFS. С production threshold 5 минут требуется соответствующая задержка.

**Исправление:** удерживать lease/heartbeat до окончания upload и terminal CAS, фиксировать finishedAt после публикации, ограничить время upload. Продумать удаление orphan objects при потере claim и неудаче persistence. Проверить recovery во время медленной публикации.

## A08 — P2: общий auth-IP лимит ниже read лимитов и ломает polling

**Место:** [apps/web/src/api.ts:65](../../apps/web/src/api.ts#L65), [api.ts:267](../../apps/web/src/api.ts#L267), [apps/web/src/ui.ts:609](../../apps/web/src/ui.ts#L609).

Любой authenticated API request сначала расходует `authIp=120/min`, затем route-specific buckets (`readUser=300/min`, `readIp=600/min`). Этот auth bucket является фактическим общим лимитом и для правильных токенов. UI опрашивает активную generation раз в секунду; любой error, включая `429`, окончательно останавливает poll без backoff/Retry-After.

**Воспроизведение:** 121-й корректно аутентифицированный GET в одном fixed window получает `429`, несмотря на ещё доступные read buckets. Две polling-вкладки за общим IP почти полностью расходуют bucket, а submit/history/download дополнительно его превышают; три создают ещё большую нагрузку. Быстрый обычный result может закончиться раньше, поэтому дефект зависит от длительности ожидания и числа клиентов.

**Исправление:** согласовать общий и route limits с polling/cohort/NAT, отделить ограничение неудачной аутентификации от успешного чтения. В UI сохранить structured HTTP status/Retry-After и ограниченно повторять transient failures. Проверить несколько пользователей за одним IP и восстановление polling после 429/503.

## A09 — P2: старый ответ polling может перезаписать новую generation в UI

**Место:** [apps/web/src/ui.ts:609](../../apps/web/src/ui.ts#L609), [ui.ts:639](../../apps/web/src/ui.ts#L639), [ui.ts:662](../../apps/web/src/ui.ts#L662).

`poll` не фиксирует generation/token/selection epoch и не проверяет его после await. Смена записи истории или запуск нового действия очищает timeout, но не отменяет уже выполняющийся request. Старый response может отобразить другой result и изменить disabled state/buttons, когда global `generationId` уже указывает на новую запись. Кнопки download/retry/revise используют именно global ID.

**Воспроизведение:** выполнена настоящая функция `poll`, извлечённая из выдаваемого `/app.js`, с управляемой задержкой API. После смены active ID на `new-generation` ответ `old-generation` отобразился и разблокировал submit. Получены `displayed=old-generation`, `activeGeneration=new-generation`.

**Исправление:** selection/request epoch плюс AbortController; применять response только к текущему ID и текущему auth context. Управлять polling через один lifecycle при terminal selection, logout и revision. Нужен interaction test с намеренно переставленными ответами; текущий `ui.test.ts` проверяет преимущественно наличие текста.

## A10 — P2: KPI «prompt-to-result» исключает время очереди и upload

**Место:** [packages/service-postgres/src/kpis.ts:144](../../packages/service-postgres/src/kpis.ts#L144), [kpis.ts:213](../../packages/service-postgres/src/kpis.ts#L213), [packages/service-core/src/worker.ts:331](../../packages/service-core/src/worker.ts#L331).

`medianPromptToResultMs` берётся из executor telemetry.durationMs. Это время pipeline после claim, а не пользовательское время от принятия prompt до доступности результата. Queue wait, upload и final persistence не включены. `finishedAt` сейчас также фиксируется до upload (A07).

**Воспроизведение:** accepted generation в 00:00, terminal в 00:30, pipeline telemetry 3 секунды. `calculateBetaKpis` возвращает medianPromptToResultMs=3000 при фактических 1 800 000 ms.

**Исправление:** сохранить отдельно execution duration, queue wait и настоящий end-to-end duration. Исправить момент finishedAt и использовать wall-clock interval для latency KPI. Документировать популяцию terminal outcomes, чтобы быстрое unsupported не маскировало latency успешных ZIP. Regression должен включать очередь и медленный store.

## A11 — P2: container smoke не соответствует текущему UI

**Место:** [scripts/test-container-web.sh:46](../../scripts/test-container-web.sh#L46), [apps/web/src/ui.ts:24](../../apps/web/src/ui.ts#L24).

Smoke ищет `Generate a Factorio mod`; фактический заголовок — `Make Factorio play your way.`. Поэтому `pnpm test:container-images` не зелёный, несмотря на успешно собранные web/worker images и живой web.

**Воспроизведение:** полный image suite упал. В отдельном повторе с bash trace оба HTTP health/page запроса прошли; последняя failing команда — `grep -Fq 'Generate a Factorio mod'`.

**Исправление:** проверять актуальный устойчивый DOM/route invariant и добавить проверку самого smoke к release gate. Не удалять smoke и не маскировать его exit code. Durable ADR не требуется.

## A12 — P2: известные advisory в dev dependencies

**Место:** root `package.json`/`pnpm-lock.yaml`, transitives Vitest и drizzle-kit.

`pnpm audit` сообщил 5 entries: две для `tinypool@1.1.1`, по одной для Vitest/@vitest/mocker 3.2.7 и esbuild 0.18.20. Vitest/mocker entries относятся к одному advisory; пять entries не означают пять независимых production exploit chains. `pnpm audit --prod` не нашёл advisory в production JS dependencies.

Две tinypool-проблемы — prototype-pollution gadgets, способные довести уже существующую pollution primitive до code execution в workers. Это риск developer/test process и потенциального будущего CI; upstream pollution primitive в этом проекте аудитом не обнаружена. Источники: [GHSA-5gmw-xhrv-c9v3](https://github.com/tinylibs/tinypool/security/advisories/GHSA-5gmw-xhrv-c9v3), [GHSA-85c8-ppgw-ccpr](https://github.com/tinylibs/tinypool/security/advisories/GHSA-85c8-ppgw-ccpr).

Vitest/mocker advisory касается development-server file reads при определённых условиях доступности/режима, а не используемого Node API. Источник: [GHSA-82fw-gwwq-j7x9](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9). Esbuild entry относится к старому dev server в транзитивной зависимости drizzle-kit: [GHSA-67mh-4wv8-2f99](https://github.com/evanw/esbuild/security/advisories/GHSA-67mh-4wv8-2f99).

**Исправление:** планово обновить поддерживаемую ветку Vitest/tooling с фактически исправленными transitives; advisory ranges сканера требуют tinypool >=2.1.2, Vitest/mocker >=4.1.11 и соответствующего исправления old esbuild path. Проверить compatibility, повторить audit и все проверки. Не ставить неподтверждённый major override в transitive graph только для обнуления счётчика.

## A13 — P3: rate-limit buckets не имеют очистки

**Место:** [packages/service-postgres/src/auth.ts:87](../../packages/service-postgres/src/auth.ts#L87), [packages/service-postgres/src/schema.ts:78](../../packages/service-postgres/src/schema.ts#L78).

Каждая новая fixed window создаёт строки по комбинации key/windowStart. В доступных runtime/scripts/Compose нет удаления старых buckets. Auth bucket создаётся и для неаутентифицированных запросов с новым IP hash. Солёное хеширование IP соблюдается, но оно не решает retention.

**Подтверждение:** проверена реализация store и поиск использования `rateLimitBuckets`/`rate_limit_buckets` и cleanup. Dynamic storage exhaustion не проводился. Фактический размер production-таблицы не проверен.

**Исправление:** retention horizon больше максимального применяемого rate window, bounded batched cleanup и наблюдение за размером таблицы. Это эксплуатационный долг перед длительной публичной работой, а не уже наблюдавшаяся авария.

## A14 — P2: локальный harness допускает traversal через info.json

**Место:** [packages/factorio-harness/src/harness.ts:65](../../packages/factorio-harness/src/harness.ts#L65), [harness.ts:153](../../packages/factorio-harness/src/harness.ts#L153).

`readModInfo` требует только непустые name/version. Затем `${name}_${version}` используется в `path.join(modsDirectory, ...)` при копировании candidate. `../` не запрещён; копирование может выйти за workRoot, а finally удаляет только workRoot.

**Воспроизведение:** минимальный local candidate с name=`../../audit-escape-<uuid>` и version=`0.1.0` скопирован harness в соседний каталог `/tmp/audit-escape-<uuid>_0.1.0`. Для безопасного теста subprocess заменён на `/bin/false`. После normal harness cleanup escaped file оставался. Аудит отдельно удалил оба своих временных каталога.

**Последствие:** local CLI/library caller, проверяющий сторонний mod directory, не получает обещанную изоляцию файловых операций. Public generation path использует application-owned safe slug/version и через этот сценарий не эксплуатировался; это не подтверждённый remote API traversal.

**Исправление:** валидировать Factorio name/version до файловых операций, проверять containment resolved destination и политику symlinks. Regression — unsafe metadata должно отвергаться до `cp`; никаких файлов вне workRoot.

## Что выдержало проверку

- HTTP submission отделён от Planner/Factorio/Repair; работа проходит через queue/worker boundary.
- PostgreSQL submission объединяет record и pg-boss job в одной транзакции; queue payload содержит generation ID.
- Runtime schemas ограничивают typed ModSpec, связность changes/assertions, supported targets и размеры manifest. Генератор application-owned и детерминированный; обычный путь не исполняет произвольный model-authored filesystem/shell agent.
- Owner checks выполняются перед чтением generation, revise/retry/feedback/download; public successful record скрывает object key и owner. Негативные ownership-сценарии в штатных API-тестах проходят.
- Токены генерируются с высокой энтропией и сохраняются как SHA-256; raw IP не служит persisted rate key. Proxy trust конфигурируется явно. Безопасность конкретного нового public proxy требует отдельной проверки topology.
- Download выдаёт короткоживущую S3-ссылку, artifact остаётся private. Отдельные S3/service integration сценарии проходят.
- ZIP manifest ограничен `info.json` и `data.lua`, companion-validation files не упаковываются. Для обычного deterministic пути real Factorio остаётся обязательным gate.
- Repair eligibility и hard cap двух attempts основаны на typed codes. Проблема A02 относится к достаточности доверительной границы Lua, а не к отсутствию cap.
- Production Node использует compiled exports с `production` condition; образы запускают приложения от пользователя `node`, worker не содержит Factorio binary на этапе image build.
- Метрики исключают metrics-ineligible users; unit/integration KPI tests проходят. Время результата требует исправления A10.
- Web использует CSP, no-store и textContent для пользовательских данных. Landing отделён от authenticated backend и намеренно не симулирует успешную генерацию.

## Дополнительные пробелы и документация

Это не дополнительные подтверждённые production-дефекты и не включено в число 14 findings:

- В checkout нет `.github` workflows. Штатные команды существуют, но автоматический merge/release gate в самом репозитории не найден. Возможная внешняя CI не проверена.
- `/health/live` — liveness, не readiness БД/queue/store. У worker нет healthcheck в beta Compose; pg-boss operational failures не имеют полного application-level reporting/alerting. Runtime heartbeat generation не равен health worker. Проверить зависший worker, возраст очереди и terminal errors до external cohort.
- Deployment docs описывают baseline PostgreSQL dump. Расписание backups, резервирование S3, restore drill, RPO/RTO и внешние alerts не подтверждены этим аудитом; конфигурация может находиться за пределами проекта.
- В beta Compose нет application CPU/memory/pid limits. Это актуальный вопрос capacity и защиты хоста при публичном ingress; безопасные значения следует измерить по Factorio нагрузке.
- `setup-factorio.sh` использует checksum-pinned официальный архив, но curl не имеет общего deadline; остановленная сеть может удерживать cold-start worker. Также install в общий cache не защищён от одновременных writers. Это важно при cold start/масштабировании.
- `docs/capabilities.md` и ранний раздел `technical-spec.md` всё ещё описывают `new_machine` узко как assembler/electric furnace, тогда как registry/domain поддерживают также drill, lab, chemical plant, refinery и centrifuge. Уточнить эти разделы по knowledge catalog. Не сокращать актуальный код до устаревшего описания.
- AGENTS содержит одновременно формулировки «M6B active» и «M6B complete». Roadmap/backlog/current-state должны обозначать один текущий gate: public ingress и external cohort после устранения дефектов.
- В landing находятся приблизительно 22 MB QA screenshots. Поскольку Docker делает широкий `COPY . .`, они попадают в image build/runtime tree, хотя публичный static build их не использует. Уточнить packaging и исключить QA artifacts из runtime при отдельной оптимизации.
- Надписи и snapshot smoke не заменяют interactive UI regression. Отдельно нужны logout/token switch, history selection, slow/reordered polls, revision/retry, structured feedback и signed download.
- Проект обещает prototype-stage validation против isolated base game. Настоящая загрузка Factorio не подтверждает баланс, достижимость созданной progression, совместимость со всеми модами/Space Age или полноту удовлетворения произвольного natural-language request. Эти границы правильно следует сохранять в beta UX.

## Рекомендуемая последовательность исправлений

1. A01: сделать HTTP boundary устойчивой к invalid URL и rejection.
2. A02: закрыть false-success Repair и согласовать durable решение/ADR.
3. A03 и A04: bounded provider/executor lifetime и terminal compensation потерянных queued jobs.
4. A05: сохранить revision snapshot на retry.
5. A06 и A07: полная изоляция runtime, heartbeat до terminal publication и orphan cleanup.
6. A08–A11: восстановление polling, stale-response guard, реальные latency KPI и зелёный container smoke.
7. A12–A14: patch dev tooling, retention и безопасные local harness paths; затем operational gates и документация.

После coherent fixes повторить narrow regressions, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm build`, service/container suites и fault-injection сценарии. Публичную topology отдельно проверить на auth/ownership, forwarding headers, TLS, доступность signed S3 URLs, quota/capacity и восстановление после restart. Принятые ADR в ходе аудита не изменялись.
